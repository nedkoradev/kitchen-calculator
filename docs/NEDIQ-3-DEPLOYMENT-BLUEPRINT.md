## Предложена инфраструктура

Използвай **Cloud Run в `europe-west1` (Белгия)**, ако собственикът потвърди, че регионът съответства на местоположението на Firestore, изискванията за данните и реалните потребители. Иначе избери потвърдения регион близо до базата, преди да създаваш ресурси. GitHub Pages остава статичният frontend. Cloud Run хоства един HTTPS endpoint зад `createWorkspaceHttpHandler`, със server-side `verifyIdToken(token, true)`. Public ingress е нужен за Firebase bearer tokens. Всеки POST изисква валиден токен и сървърно проверена пилотна allowlist по UID над съществуващите роли. Allowlist по `Origin` е браузърна граница. Тя не замества проверката на токена или UID.

- В отделен staging проект или база създай runtime service account с отделна идентичност от тази за deploy. Runtime използва Application Default Credentials. Не създавай JSON ключ. Измери минималните разрешения за Firestore транзакции и `firebaseauth.users.get` за проверка на revoke. Валидирай най-тясна custom role с `datastore.entities.get/list/create/update/delete` и нужните permissions на базата за транзакции. Ограниченията на Firestore IAM не са надежден заместител на изолацията по колекции при Admin SDK. Ако ресурсите не могат да се ограничат достатъчно, използвай отделна одобрена база или проект и прекъсни rollout към основната база.
- За пилот започни с 0 минимални и 2 максимални инстанции, concurrency 8 и timeout 30 s. Потвърди 900 KB HTTP и 800 KB транзакционен лимит. Включи ограничение по UID/IP на входа и квоти след измерване върху синтетични документи. Не разчитай на бюджетните аларми за спиране на разходите.
- Следи request rate, p95 latency, 5xx, 401/403, конфликти, дълго висящ журнал, брой Firestore четения/записи и разходи. Настрой нисък одобрен бюджет с аларми на 50%, 80% и 100%. При аномалия блокирай първо записите на пилота. Не логвай request bodies, заглавки Authorization, имейли, изходни документи или тайни.
- Собственикът потвърждава Firestore project/database/location, origin, service account, IAM ограничения, Auth provider настройки, quota, retention, on-call контакт и бюджета. Пилотна allowlist и реален Cloud Run deployment остават активационна стъпка. Няма създадени ресурси.

## Предложени съставни правила

`node rollout-preflight/composite-rules.mjs > /path/to/private/workspace-composite.rules` генерира прегледаемото предложение. `diff -u firestore.rules /path/to/private/workspace-composite.rules` показва само добавения v3 блок. Съществуващият v2 файл остава неизменен. В v3 директните клиентски записи са отказани за всички роли. Довереният сървър проверява право за запис, нормализирани имена, ревизии и транзакционен журнал. Authenticated тестовете проверяват и запазване на достъпа до v2. При различие между Git и реалния файл състави нов diff върху одобрено копие и повтори тестовете. Няма автоматична стъпка за deploy.

## Локален архив на вече одобрено копие

Инструментът няма мрежов клиент. Той приема само съществуващ локален файл. Създаването или получаването на копие от production е отделна одобрявана операция извън този workflow.

1. Определи конкретни собственик, обхват и срок на задържане. Използвай частен локален каталог на криптиран диск с `umask 077`. Не поставяй копия в репото, CI артефактите или синхронизиран публичен каталог. Запиши UTC прозорец, очаквани бройки и източник в частния протокол.
2. Форматът е UTF-8 JSON обект с `ownerUid`, `projects` и `cabinets` като масиви `[{id, record, catalog?}]`, `folders` с legacy папки, `drafts` като `[{scope, bundle}]` и налични `grants`, `materials`, `settings`. В `grants` използвай одобреното преобразуване email → UID и роли editor/viewer. Историческият каталог на шкафа се предоставя изрично, когато записът няма каталог. Остави timestamp и историята в договорения JSON формат. Входът за един локален пакет е до 64 MiB.
3. Провери явните контроли преди пакетиране: брой и типове записи, съвпадение на права и owner scope, четимост на JSON, валиден исторически каталог, наличие на двете legacy чернови и оригинални координати. Пази независимо архивно копие на източника.
4. Подай силна уникална парола чрез fd 3. Примерът използва Bash без изписване на паролата. Дръж паролата в одобрен мениджър отделно от архива.

```bash
umask 077
read -rs NEDIQ_ARCHIVE_PASSPHRASE
node rollout-preflight/backup.mjs pack /private/approved-copy.json /private/pilot.enc \
  3< <(printf '%s' "$NEDIQ_ARCHIVE_PASSPHRASE")
node rollout-preflight/backup.mjs verify /private/pilot.enc \
  3< <(printf '%s' "$NEDIQ_ARCHIVE_PASSPHRASE")
sha256sum /private/pilot.enc
unset NEDIQ_ARCHIVE_PASSPHRASE
```

Manifest с час, бройки, SHA-256 и размер на оригиналните байтове е в автентикирания AES-256-GCM пакет. Външният SHA-256 е за проверка на преноса. Сравни го на независимо защитено хранилище. `verify` проверява GCM тага и хеша, без разшифрован файл. `unpack` пише само нов файл с ограничени права. Използвай го за dry-run в частната зона, после премахни временната декриптирана работна версия по одобрения план.

## Изолиран staging и fallback

`npm run test:release-emulator` упражнява локалния staging с реалния Firebase Auth SDK срещу Auth Emulator, журнал и запис през доверения HTTP handler към Firestore Emulator. Входът е през автентикиран потребител, без тестов избор на профил. Email/password е проверен с клавиатура. Бутонът за Google използва същия Firebase Auth интерфейс, а production Google OAuth конфигурацията и popup потокът остават за проверка при отделно одобрение.

`node rollout-preflight/stage-server.mjs` обслужва loopback fallback с v2.95 renderer, без cloud, локално нулиране и worker. В shell на двата локални емулатора `node rollout-preflight/stage-server.mjs --enabled` добавя локалния staging на порт 8053. `/fallback` запазва изолирания стар renderer. Без флага няма v3 API. При недостъпен журнал командите остават блокирани и черновата се пази. Работещият `index.html`, публичният label и кеш метаданните не се редактират. Реалният fallback при rollout е потвърденият Pages SHA на v2.95.

## Пилот и отделни разрешения

| Решение | Действие след съответното одобрение | Критерий |
| --- | --- | --- |
| 1. Export | Собственикът разрешава read-only копие за един назован потребител и точно избрани колекции. Пакетирай локално и провери SHA, броя и възстановяването. | Архивът е проверен и има независим втори екземпляр. |
| 2. Infrastructure | Създай одобрения Cloud Run staging endpoint, service account, бюджет, алерти и UID allowlist. | Точният origin и ID token се проверяват, outsider е отказан, нулев cache на данни. |
| 3. Rules deploy | Сравни live и Git, състави diff върху одобрената база, прегледай v2/v3 и пусни authenticated тестовете. Запази одобрените правила за rollback. | Няма регресия на v2, преки v3 записи се отказват, правата след revoke са ограничени до собствен журнал. |
| 4. Migration | В частната зона `node release-candidate/dry-run.mjs /private/approved-copy.json`. Свери бройки, ID, права, каталози, групи, разкрой, себестойност, история и rollback. Мигрирай само одобрения пилот. | Нула блокери, пълно съпоставяне, успешен reload, запазени оригинали, потвърден rollback. |
| 5. Pages publish | Отделно одобри activation diff, публичния номер и кеш SHA. Първо провери защитения staging, после публикувай точния activation SHA чрез `pages.yml`, с проверка на публичния `release.json`, кеша и входа на пилота. | Пълни зелени проверки, потвърден SHA, наблюдение и бутони за спиране на записите. |

При no-go спри първо v3 записите. Архивирай пилотния журнал и новите v3 документи. Възстанови одобрения v2.95 SHA и неговия cache чрез Pages само след разрешение. Свери версията, записването във v2 и положението на черновите. Връщане на правилата е самостоятелно одобрявана операция. Докато пилотът не е приет, не разширявай cohort и не изтривай v2 данни.
